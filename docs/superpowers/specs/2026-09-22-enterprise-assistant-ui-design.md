# 企业总助手、意图识别与前端升级设计

日期：2026-09-22

适用基线：`05bc7cd`

## 1. 本次决策

本轮建设聚焦四项内容：

1. 取消低代码工作流建设，不开发流程画布、通用节点市场和新的低代码执行引擎。
2. 首页增加“企业总助手”，作为员工使用平台知识、系统工具和专业智能体的统一对话入口。
3. 增加显式意图识别和能力路由，避免把所有工具与数据直接交给模型自由选择。
4. 全面统一前端视觉、布局、交互状态和响应式体验。

单点登录本轮不做。复杂业务仍按业务需求开发专业智能体，可内置于当前模块化单体，也可通过受控的 HTTP Runner 接入平台；A2A 不是当前依赖。

## 2. 取消低代码的处理边界

“取消”指停止继续建设低代码平台，不是立即删除当前已经运行的顺序工作流：

- 不新增拖拽画布、分支编排、节点市场、低代码发布中心。
- 智能体工作室不再提供新建“工作流智能体”的入口。
- 已有 `workflow_run`、相关 API、历史记录和运行代码暂时保留为兼容层，防止已有数据丢失。
- 如果确认线上不存在仍需使用的工作流，再单独执行带备份和迁移检查的清理任务。
- 知识问答、MCP、模型网关、专业智能体、评测、审计和运行追踪继续保留。

这样既贯彻新方向，也不以一次前端调整触发破坏性数据库删除。

## 3. 企业总助手定位

企业总助手是平台级调度入口，不替代现有专业智能体。员工仍可直接进入人资问答、ERP 助手等专业智能体；当员工不知道该用哪个入口时，由总助手识别需求并选择合适能力。

总助手可使用的能力始终是当前用户权限范围的交集：

- 用户可访问的知识库；
- 用户获授权的只读 MCP 工具；
- 用户可使用且已发布的专业智能体；
- 已启用的声明式 Skill；
- 普通大模型对话能力。

总助手不能因为“看见了某个能力”而扩大用户权限，也不能绕过现有部门权限、智能体授权、MCP 工具授权和审计规则。

## 4. 一次请求的完整链路

```text
用户问题
  → 加载用户与部门权限
  → 构造授权能力目录
  → 意图识别（结构化输出）
  → 后端校验候选能力与参数
  → 需要时向用户澄清
  → 执行知识检索 / MCP 工具 / 专业智能体 / 普通对话
  → 汇总结果、来源与执行摘要
  → 保存会话、意图、运行记录和审计日志
```

路由阶段只向模型提供精简的候选能力摘要，不把全部工具定义、全部知识库和所有智能体一次性放入上下文。先做权限过滤，再做候选召回，最后让路由模型从少量候选中选择。

## 5. 意图识别

### 5.1 意图类型

第一版固定为以下类型：

| 类型 | 含义 | 示例 |
| --- | --- | --- |
| `general_chat` | 不需要企业数据的普通交流 | “帮我润色这段话” |
| `knowledge_query` | 查询制度、技术资料、项目文档 | “年假怎么申请” |
| `system_query` | 调用 ERP、OA、MOM、PLM 等只读工具 | “查询物料 123 的可用库存” |
| `agent_task` | 交给一个已发布专业智能体 | “分析这份标书的风险” |
| `multi_capability` | 需要两种以上能力协作 | “结合 OA 审批和制度说明未通过原因” |
| `clarification` | 缺少组织、物料、时间范围等关键参数 | “帮我查库存” |
| `forbidden` | 请求超出权限或属于当前禁止的写操作 | “替我直接修改 ERP 库存” |

### 5.2 结构化决策

路由模型必须输出受 JSON Schema 约束的结果，包含：

- 意图类型；
- 置信度；
- 候选知识库、工具、智能体或 Skill 标识；
- 缺失参数；
- 是否需要澄清；
- 风险级别和简短原因。

后端不信任模型输出。所有标识必须属于授权能力目录，参数必须按工具 Schema 校验；无效标识丢弃并记录。低置信度、多义请求或缺少关键参数时，先询问用户，不猜测执行。

### 5.3 执行约束

- 第一版只自动执行只读系统工具。
- 写入 ERP、OA、MOM、PLM 的动作不纳入本轮自动执行。
- 限制单次请求的模型轮数、工具次数、智能体委托数、总时长和 Token 用量。
- 专业智能体调用时沿用当前用户身份、部门、根运行 ID 和剩余预算。
- 知识检索继续使用现有部门权限、混合检索、RRF、重排序和引用链路。
- MCP 结果必须标记来源系统、工具名、调用时间和关键参数摘要。

## 6. Skill 的最小定义

本轮不引入可执行任意代码的 Skill 市场。Skill 是管理员维护的“声明式业务能力包”，内容包括：

- 名称、说明、适用场景和触发示例；
- 版本化系统指令与输入参数 Schema；
- 允许使用的知识库、MCP 工具和专业智能体；
- 授权部门、状态和版本；
- 测试样例与发布记录。

Skill 本身不能执行 Shell、原始 SQL 或任意 URL。复杂算法、长任务和专业业务逻辑仍由经过测试的专业智能体实现，Skill 只负责把已有受控能力组合成可复用的业务说明。

## 7. 对话、任务与可追溯性

企业总助手复用现有持久化对话和异步任务机制：

- 支持新建、重命名、删除和恢复会话；
- 切换页面或刷新后，问题、回答中状态和最终结果保持一致；
- 每次请求记录意图决策、选中能力、权限校验、耗时、错误和引用；
- 工具与专业智能体的详细过程默认折叠，用户可展开查看；
- 管理员可在运行追踪和审计日志中定位一次请求的完整链路。

后端通过保留代码为 `ENTERPRISE_ASSISTANT` 的平台智能体复用现有会话模型；它不使用静态知识库绑定，而是在每次请求时计算当前用户的授权能力快照。为每次运行保存能力快照和意图决策，保证事后可解释。

## 8. 后端改造

新增独立领域模块 `domains/assistant`，职责边界如下：

- `capability_catalog`：汇总并过滤用户可用的知识库、工具、智能体和 Skill；
- `intent_router`：候选召回、结构化意图识别、置信度与澄清策略；
- `orchestrator`：按路由结果调用现有检索、MCP 和智能体运行接口；
- `repository`：保存意图决策、能力快照和运行关联；
- `router`：提供总助手会话、消息、任务状态和能力摘要 API。

现有知识检索、MCP 调用和专业智能体运行逻辑不复制到新模块，而是通过明确的应用服务接口复用。总助手只负责编排与权限复核。

数据库采用渐进迁移：

- 复用现有聊天会话、消息、任务和运行表；
- 新增意图决策记录与声明式 Skill 相关表；
- 不改动现有知识库、文档、切片、Milvus 集合和 OpenSearch 索引；
- 不删除工作流表和历史数据；
- 所有新增迁移可重复检查、可回滚，并登记到迁移台账。

## 9. 前端整体升级

### 9.1 设计系统

继续使用 Vue 3 和 Vue Router，不为换皮引入沉重框架。建立统一基础组件和设计变量：

- 颜色、字号、间距、圆角、阴影和层级；
- Button、Input、Select、Modal、Card、Badge、Table、EmptyState、Skeleton、Toast；
- 统一 SVG 图标，移除不一致的字符图标；
- 统一加载、空数据、错误、无权限、禁用和危险操作状态；
- 支持常见桌面分辨率，并在窄屏自动收起侧栏和重排表单。

视觉方向采用克制的企业后台风格：深蓝导航、浅灰蓝工作区、蓝色主操作、明确的信息层级和更充足的留白。避免过度渐变、巨大卡片和装饰性动画。

### 9.2 首页

首页由“统计看板”升级为实际工作入口：

- 中央为企业总助手对话区；
- 左侧为会话列表，支持新建、搜索、重命名和删除；
- 首屏提供常用问题和能力快捷入口；
- 回答显示引用来源、调用的知识库/工具/智能体标签；
- 执行步骤以可折叠时间线展示；
- 右侧展示当前可用能力、最近任务和系统状态；
- 回答中离开页面再返回时，状态与内容继续同步。

### 9.3 其他页面

- 智能体：使用响应式卡片网格，一行约 4 个入口；进入详情后再开始交互。
- 知识库：知识库选择置顶，目录树、上传区、资料表格层级清楚，避免横向拥挤。
- 系统连接、大模型网关、提示词模板、申请、用户、审计：统一筛选栏、表格、详情抽屉和表单布局。
- 管理功能与普通员工功能保持清晰分区，菜单和按钮继续由服务端权限决定。
- 页面按路由拆分并懒加载，避免导航切换重建无关状态。

## 10. API 与界面契约

总助手使用独立命名空间，避免与具体智能体聊天接口混淆：

- `GET /api/v1/assistant/capabilities`：返回当前用户可见的能力摘要；
- `GET/POST /api/v1/assistant/sessions`：会话列表与新建；
- `PATCH/DELETE /api/v1/assistant/sessions/{id}`：重命名与删除；
- `GET /api/v1/assistant/sessions/{id}/messages`：消息与运行状态；
- `POST /api/v1/assistant/sessions/{id}/messages`：提交问题；
- `GET /api/v1/assistant/tasks/{id}`：异步任务状态和执行摘要；
- 管理员 Skill API 置于 `/api/v1/admin/skills`。

所有响应沿用项目统一错误格式、请求 ID、时间字段和权限拒绝语义。

## 11. 测试与验收

必须覆盖：

1. 权限过滤后，路由模型看不到未授权知识库、工具、智能体和 Skill。
2. 模型返回越权或不存在的能力标识时，后端拒绝执行并留下审计记录。
3. 低置信度和缺少关键参数时，系统提出澄清问题。
4. 知识问答、MCP 查询、专业智能体委托和混合请求分别走正确链路。
5. 多员工并发会话相互隔离，不能读取彼此消息和任务状态。
6. 页面切换、刷新和重新登录后，正在回答和已完成内容正确恢复。
7. 前端在常见分辨率下无遮挡、溢出、按钮折行和不可操作区域。
8. 原有登录、知识库上传、检索问答、模型网关、MCP、用户权限、审计和评测回归通过。
9. 已有工作流数据未被迁移删除，旧接口保持兼容但前端不再新增入口。

## 12. 实施顺序

1. 冻结低代码入口并建立兼容边界。
2. 建立总助手能力目录、意图决策模型和权限测试。
3. 接入现有知识检索、MCP 与专业智能体运行服务。
4. 完成总助手持久化会话和任务状态恢复。
5. 重做首页和统一前端基础组件，再逐页迁移视觉与交互。
6. 完成端到端、权限、并发和回归验证后部署。

## 13. 本轮明确不做

- 单点登录；
- 低代码流程画布和通用工作流平台；
- Kubernetes、微服务拆分和通用消息中间件；
- 自动执行 ERP、OA、MOM、PLM 写操作；
- 强制引入 A2A；
- 一次性删除旧工作流数据库与运行代码；
- 允许 Skill 执行任意代码、SQL 或外部 URL。
