# 遗留功能与数据清理设计

## 目标与范围

彻底移除已取消的低代码工作流：不仅隐藏前端，还删除创建、运行、审批、后台领取和数据库表。顺手收敛明确无用的同步问答 API、旧角色/部门分发表和重复模型、检索配置字段。保留知识问答、企业总助手、评测、MCP 工具、账号权限、文档及索引。已发布的 `001`–`014` 迁移不可改写。

本轮包含生产库物理删表，但以备份、行数及权限对账、应用兼容切换和验收为门槛。任何门槛失败就停，不强行清除。已存在的用户临时文件、模型缓存、MinIO 对象、Milvus/OpenSearch 索引和 Redis 留存数据不在本轮删除范围。

## 已核对的事实（2026-10-07）

- 生产 `workflow_run`、工作流智能体和含工作流配置的 `agent_revision` 均为 0；但 API、Vue `WorkflowRun.vue`、工作室步骤编辑和后台 runner 仍能执行工作流。
- `app_role` 3 行、`user_role` 13 行、`agent_department_acl` 2 行；当前授权依赖部门管理员身份及用户级 ACL。旧部门智能体授权已回填，缺失映射为 0。
- `document_asset` 为 0 行且运行代码无读写引用；`document_department_acl` 仍在文档、Worker 和检索链路使用，必须保留。
- `agent.llm_model` 没有非空值；`agent.agent_type` 只是对 `launch_mode` 的重复分类。`agent_knowledge_base.retrieval_config_json` 有 1 条仍作为运行时回退，不能直接丢弃。
- `/api/v1/agents/{id}/chat` 是已标记废弃的同步入口；正式前端用持久化 `/runs`。总助手不会调用专业智能体，遗留 `agent_task` 类型仅用于历史记录兼容展示。

## 方案取舍

采用“先迁有效数据、再切代码、最后删结构”的两阶段迁移。直接删表最快，但旧进程仍可能访问 `workflow_run` 且检索配置会丢失；永久保留旧表风险最低但不满足明确的清理要求。两阶段方案允许在同一轮真正删除，同时给验证失败留出停点。

## 代码与接口

1. `AgentWrite` 只接受 `chat`；提交 `workflow` 必须得到 422，不能静默转成问答。删除工作流步骤、输入和参数校验。API 删除三个 workflow-runs 路由以及同步聊天路由；旧调用得到 404。
2. `StudioService/Repository` 只保留评测和知识库处理设置；把混合文件 `runtime/workflows.py` 缩为评测 runner（按职责命名），`chat_tasks` 只领取聊天和评测。评测授权、短事务与审计行为不变。
3. Vue 移除工作流运行组件和工作室步骤编辑/历史兼容文案，智能体列表只展示当前问答入口。旧配置版本仍可查看；恢复含工作流配置的历史版本必须由后端拒绝。历史审计记录不删。
4. 删除仅服务于同步聊天的参数、审计分支和接口测试。异步会话、任务重试、取消和回答持久化保持不变。
5. 总助手的新意图不再输出 `agent_task`，历史决策记录可读但不能据此委派工具或扩大权限。

## 数据迁移与部署顺序

`015` 是非破坏性准备迁移：把每个仍依赖旧 `retrieval_config_json` 的智能体有效策略并入 `settings_json.retrieval`，已有新字段优先；迁移前后以真实 `RetrievalPolicy` 值逐项比较，不只比较 JSON 文本。若某智能体在多个知识库绑定上存在不同旧策略且无新策略，则旧查询没有稳定排序，迁移必须中止并人工确定有效配置，不能自行取其中一条。其他业务表不动，旧应用仍可运行。

`016` 是经预检后执行的退役迁移：确认无工作流运行/智能体/版本、旧 ACL 回填缺失为 0、所有有效检索配置已迁好，并验证备份可读；随后删除 `workflow_run`、`user_role`、`app_role`、`agent_department_acl`、`document_asset`，及 `agent.llm_model`、`agent.agent_type`、`agent_knowledge_base.retrieval_config_json`。`user_role` 先于 `app_role` 删除以满足外键顺序。保留 `document_department_acl`、`user_*_acl`、`agent_revision`、`chat_task`、`evaluation_*`。

在生产操作前，先对当前 MySQL 整库生成不含明文凭据的受限备份，记录大小和 SHA-256，并通过临时库导入/关键表计数证明备份可恢复；不得把备份提交 Git。执行 `015`、核对策略；发布不再引用目标结构的新 API/Worker/前端；验证登录、部门/用户权限、历史对话、问答、检索评测及健康；暂停可能运行的后台任务或在维护窗口确认清空，再执行 `016` 并重新验证。若任一步失败，停止后续步骤，依阶段采用前向修复或从备份恢复；删表后不能只回滚应用镜像。

全新 MySQL 按编号执行 `001`–`016`；新迁移不能修改已应用脚本。当前手工迁移 runner 不记录台账，执行前必须读取 `information_schema` 判断状态，不重复运行 DDL；本轮补迁移台账/执行说明及预检脚本，以避免误操作。

## 验收标准

- OpenAPI 和 Vue 中无可用的工作流创建、运行、审批及同步问答入口；直接提交旧模式得到 422，旧路由得到 404。
- 后台领取队列只有 `chat_task`、`evaluation_run`；检索评测仍可提交、完成和读取。
- 清理前后有效检索策略相同；账号、知识库、智能体和 MCP 权限无扩大；文档、向量、全文索引计数不因迁移变化。
- 备份恢复演练与授权对账通过后才执行 `016`；执行后目标表/列不存在，保留表仍存在。生产健康与核心业务烟测通过。
- 自动化 Python/Vue 测试、前端 typecheck/lint/build、迁移冷启动与既有库升级测试通过；文档不再把已删除功能称作兼容层。
