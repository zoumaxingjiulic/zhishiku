# 企业智能体平台混合运行与低代码工作流设计

日期：2026-09-21

适用基线：`53162ee`

## 1. 背景与目标

平台已经具备部门权限、知识库、混合检索、模型网关、MCP 连接器、持久化对话、配置版本、顺序工作流、人工确认、评测、运行追踪与审计。现有运行时适合知识问答和步骤较固定的流程，但缺少两项平台级能力：

1. 无法以统一契约接入由 Python、Java 或专用框架开发的复杂智能体。
2. 当前工作流只能按顺序执行，不能表达条件分支、子流程、失败处理和复杂智能体调用，也没有可视化编排入口。

本设计采用混合架构：

- 平台控制面统一管理身份、权限、模型、知识、工具、版本、审计和用量。
- 低代码工作流执行确定、可审计、可恢复的业务流程。
- 复杂智能体作为独立 Runner 服务实现开放式推理、专业算法和长任务。
- 工作流可以调用复杂智能体；复杂智能体可以通过平台能力网关调用模型、知识库、MCP 和已发布工作流。

目标不是让所有能力都低代码化，也不是把所有智能体代码塞入现有 FastAPI，而是建立稳定、语言无关、可治理的组合边界。

## 2. 使用者和治理边界

平台区分三类使用者：

| 使用者 | 允许能力 |
| --- | --- |
| 普通员工 | 使用已发布智能体和流程，查看本人任务、审批请求与结果 |
| 业务骨干/实施人员 | 在授权模板内配置表单、提示词、确定性节点和有限参数，提交发布申请 |
| 技术人员/平台管理员 | 开发复杂智能体与受信节点，配置权限、测试、评测、发布、停用和回滚 |

第一阶段只有平台管理员可以创建、修改和发布工作流与复杂智能体。业务骨干能力在权限模型、模板和发布审批稳定后开放。普通员工永远不能创建任意代码、原始 SQL、任意 HTTP 或绕过平台网关的模型节点。

## 3. 方案选择

### 3.1 不采用全低代码

全低代码适合短流程和常见节点，但不适合复杂文件处理、专业算法、多轮自主规划、长时间运行、多智能体协作及大量自定义状态。把这些逻辑塞入画布会形成难以测试、审查和复用的巨型流程。

### 3.2 不采用全代码孤岛

每个智能体独立实现登录、权限、模型、知识库、MCP、审计和页面，会产生重复治理和安全边界不一致。只在平台中放外部链接也无法提供统一身份、运行记录、审批与成本管理。

### 3.3 采用混合架构

```text
统一入口与控制面
├── 用户、部门与授权
├── Agent 目录、发布与版本
├── 模型网关、知识检索、MCP Broker
├── 任务、事件、审批、产物
└── 审计、评测、用量和成本
          │
          ├── 内置对话运行时
          ├── 低代码工作流运行时
          └── 远程复杂智能体 Runner
```

低代码负责“怎样组织能力”，复杂智能体负责“专业能力本身”，平台负责“谁能用、能访问什么、如何运行及如何追溯”。

## 4. 能力边界

### 4.1 知识库

知识库只负责有权限约束的非结构化资料检索、证据返回和引用，不负责业务流程编排或任意系统操作。

### 4.2 MCP 与连接器

MCP 工具表示边界明确的能力，例如查询库存、读取 OA 人员、获取 BOM 或创建业务单据。MCP 不是复杂智能体的长任务协议。写工具必须具备服务端数据权限、参数校验、幂等键、人工审批和审计，不能只依赖 `readOnlyHint`。

### 4.3 低代码工作流

工作流表达步骤已知、规则明确、需要审计和人工控制的过程。确定性校验、金额计算、权限判断和系统写入由确定性节点或受信工具执行，不能由模型自由文本决定。

### 4.4 复杂智能体

复杂智能体用于步骤不能完全预先确定的任务，包括动态规划、多轮检索、专业算法、专用 SDK、多智能体协作、长时间处理和多产物生成。它可以使用 LangGraph、AgentScope、自研状态机或普通业务代码，但必须遵守平台接入契约。

## 5. 控制面与执行面

### 5.1 平台控制面

现有 FastAPI 继续作为统一控制面，负责：

- 智能体注册、部门 ACL、知识库与工具授权。
- 模型配置、调用额度和供应商凭据。
- Runner 注册、健康状态、能力清单和版本。
- 运行创建、取消、审批、事件查询与产物登记。
- 评测、审计、用量、成本和发布门禁。

控制面不执行远程复杂智能体的专业代码，也不向 Runner 暴露数据库或外部系统长期凭据。

### 5.2 执行面

执行面包含三种执行器：

1. `builtin_chat`：现有知识问答与受控 MCP 工具调用。
2. `builtin_workflow`：平台持久化工作流运行时。
3. `remote_agent`：独立 Docker 服务中的复杂智能体。

用户面对的 `agent` 仍是唯一目录实体；发布配置指定执行器类型和执行器档案。交互形式 `chat/form/workflow/dashboard/external` 与执行器类型相互独立，例如表单入口也可以启动远程智能体。

## 6. 复杂智能体接入协议

### 6.1 Runner 能力清单

每个 Runner 注册不可变代码、名称、版本和能力清单：

```json
{
  "protocol_version": "1.0",
  "code": "BID_ANALYSIS_AGENT",
  "version": "1.2.0",
  "input_schema": {},
  "output_schema": {},
  "supports_streaming": true,
  "supports_cancel": true,
  "supports_approval": true,
  "artifact_types": ["report", "document", "spreadsheet"]
}
```

输入输出使用受限 JSON Schema。平台发布智能体前校验配置与 Runner 清单兼容；Runner 升级不能静默破坏已发布智能体版本。

### 6.2 Runner HTTP 契约

第一版使用平台内网 HTTPS/HTTP JSON + SSE，不要求所有 Runner 立即实现 A2A。接口语义为：

```text
GET    /v1/manifest
GET    /v1/health
POST   /v1/runs
GET    /v1/runs/{external_run_id}
GET    /v1/runs/{external_run_id}/events
POST   /v1/runs/{external_run_id}/cancel
POST   /v1/runs/{external_run_id}/actions
```

- `POST /runs` 必须接受平台 `run_id` 和幂等键，重复请求返回同一外部运行。
- `events` 使用 SSE，事件具有单调递增序号，断线后可用 `Last-Event-ID` 恢复。
- `cancel` 和 `actions` 必须幂等；不支持取消的 Runner 在清单中显式声明。
- 平台为远程运行设置连接超时、心跳超时、总时限和最大事件/产物大小。
- 后续可增加 A2A 适配器，但 A2A 不是第一版的前置依赖。

### 6.3 委托身份

平台为每次运行签发短期、单次作用域令牌，至少包含：

```text
actor_user_id
department_ids
agent_id
agent_revision
run_id
allowed_knowledge_base_ids
allowed_tool_ids
allowed_model_profile_id
expires_at
audience
```

Runner 只能凭该令牌调用平台能力网关。平台每次调用重新加载当前账号、部门和绑定关系，令牌只限制上限，不能替代实时服务端授权。撤权、停用、任务取消或版本变化后，后续调用必须被拒绝。

每次委托还必须携带根运行 ID、父运行 ID、调用深度和剩余预算。平台禁止直接或间接调用正在祖先链中的同一“智能体版本/工作流版本”，并限制最大委托深度、子运行数、模型 Token、工具次数、累计时长和产物大小，防止智能体与工作流相互调用形成无限递归或失控成本。

### 6.4 平台能力网关

复杂智能体通过内部 SDK/API 使用：

- 模型生成与结构化输出。
- 权限过滤后的知识检索。
- 已绑定 MCP 工具调用。
- 人工审批请求与结果。
- 运行事件和指标上报。
- 产物上传与登记。
- 已发布工作流调用。

Runner 不直接持有 MySQL、MinIO、Milvus、OpenSearch、ERP、OA、PLM、MOM 或模型供应商凭据。产物经平台签发的短期上传权限或平台代理上传，最终保存到 MinIO，并在 MySQL 保存元数据、所有者和保留策略。

## 7. 统一运行模型

### 7.1 运行状态

聊天、工作流和远程智能体逐步统一到以下外部状态：

```text
queued
running
waiting_approval
succeeded
failed
cancel_requested
cancelled
timed_out
```

内部执行器可以保留自己的细分状态，但 API 与前端只依赖统一状态和事件。运行记录固定关联用户、部门快照、智能体发布版本和执行器版本，不能在运行中自动切换到新配置。

### 7.2 统一事件

事件采用只追加模型：

```text
run.started
stage.started
stage.completed
retrieval.started
retrieval.completed
model.started
model.completed
tool.requested
tool.completed
agent.delegated
approval.required
approval.resolved
artifact.created
message.delta
run.completed
run.failed
run.cancelled
```

每条事件包含 `run_id`、序号、时间、事件类型、阶段标识、脱敏负载和追踪 ID。敏感提示词、凭据和业务系统原始响应不得写入事件。`message.delta` 可以短期传输流式文本，但是否持久化及保留期限由数据策略决定；最终结果必须原子发布。

### 7.3 产物

复杂智能体输出不局限于聊天文本。平台统一管理报告、DOCX、PDF、XLSX、图片和结构化数据产物，记录：

- 运行、创建者、所属部门和智能体版本。
- MinIO 对象键、媒体类型、大小和校验和。
- 安全级别、保留期限和下载权限。
- 生成状态及病毒/格式检查状态。

前端只通过授权下载接口访问产物，不直接暴露对象存储凭据。

## 8. 工作流模型

### 8.1 第一阶段节点

第一版图执行语义支持：

- `start` / `end`
- `model`
- `knowledge_retrieval`
- `mcp_tool`
- `condition`
- `transform`
- `human_approval`
- `agent_call`
- `subflow`

`agent_call` 调用已发布的复杂智能体版本；`subflow` 调用已发布工作流版本。节点通过显式输入输出 JSON Schema 和变量映射连接，不允许隐式读取其他节点内部状态。

### 8.2 暂不开放的节点

第一阶段不提供任意 Python/JavaScript、原始 SQL、任意 URL HTTP 和任意 shell 节点。确有专业需求时，由技术人员开发受信的远程智能体、MCP 工具或经过审核的自定义节点包。

### 8.3 图约束

- 定义必须是有向图，发布时进行节点、边、类型、变量、可达性和循环检查。
- 第一版允许条件分支和分支汇聚，不允许任意循环；循环在具备步数、时限和预算控制后单独设计。
- 每个节点声明超时、最大重试次数和失败策略。
- 写工具节点默认前置人工审批，不得由画布配置关闭平台强制策略。
- 子流程和智能体调用固定到发布版本；新版本只影响新运行。
- 工作流定义、画布布局与执行快照分离，布局变化不改变执行语义。

### 8.4 执行与恢复

工作流运行时以 MySQL 为事实来源。节点状态和输出在步骤边界持久化；Runner 崩溃后从最后一个已提交边界恢复。每个外部副作用使用稳定幂等键：

```text
workflow_run_id:node_id:attempt_group
```

重试只重复允许重试的节点。对不可自动回滚的写操作使用补偿任务或人工处置，不宣称跨 MySQL、MCP 和业务系统的分布式事务。

## 9. 可视化编排器

画布是工作流定义的编辑器，不是执行引擎。只有图模型、校验、版本和恢复语义稳定后才建设完整画布。

前端使用与 Vue 技术栈兼容的图组件，负责：

- 拖放受信节点、连接边和配置变量映射。
- 节点级 schema 表单、校验错误和权限提示。
- 使用草稿输入运行单节点或完整流程测试。
- 展示每个节点状态、耗时、脱敏输入输出和错误。
- 比较草稿与已发布版本，发布前显示权限与副作用摘要。

前端不能自行决定可用节点、工具和知识库；所有选项和校验以服务端返回的能力目录与发布校验结果为准。

## 10. Agent 市场与发布

智能体目录升级为受治理的 Agent 市场，但继续使用现有 `agent` 作为业务入口。每个条目展示：

- 类型、负责人、所属部门和授权部门。
- 执行器类型、发布版本和运行状态。
- 绑定知识库、工具和模型的摘要。
- 输入形式、预期产物和是否包含写操作/审批。
- 使用次数、成功率、平均耗时和最近更新时间。

发布过程为：

```text
草稿 → 配置校验 → 连接/节点测试 → 评测 → 权限与副作用审查
     → 管理员发布 → 灰度/正式使用 → 监控 → 回滚或停用
```

工作流、复杂智能体清单、授权和模型绑定都保存到不可变发布快照。回滚产生新的发布记录或重新激活已验证版本，不覆盖历史。

## 11. 安全与隔离

- Runner 地址沿用精确主机/CIDR 白名单、DNS 固定、重定向拒绝和网络 ACL；不得允许用户填写任意执行地址。
- Runner 凭据和签名密钥加密保存且永不回显，生产环境使用独立服务身份。
- 控制面在任务创建、能力调用、结果发布和下载产物时重新授权。
- 子运行继承父运行授权上限，只能进一步收窄，不能通过调用其他智能体扩大知识库、工具、模型或数据权限。
- 所有输入按 schema 限制大小、层级、数组长度、文件数和媒体类型。
- MCP/Runner 返回内容视为不可信数据，进行结构、大小、内容类型和日志脱敏校验。
- 远程 Runner 默认在独立容器运行，设置 CPU、内存、并发、超时和只读文件系统；按需要挂载专用临时目录。
- 不允许 Runner 直接访问其他 Runner。智能体协作通过平台 `agent_call` 能力完成，形成统一审计链。

## 12. 错误处理和可观测性

每次运行统一记录：

- 排队、执行、模型、检索、工具、审批和远程 Runner 耗时。
- 输入输出 Token、模型成本估算和工具调用计数。
- 重试、取消、超时、失败分类和最终状态。
- 智能体、配置版本、Runner 版本和追踪 ID。

错误分为可重试基础设施错误、不可重试输入错误、权限变化、取消、超时、业务拒绝和未知错误。前端显示稳定错误码和安全文案；内部日志通过追踪 ID 关联，不返回堆栈、凭据、内部地址或业务正文。

远程 Runner 心跳中断时，平台先标记运行状态不确定并在有限时间内核验，不立即重复启动可能产生副作用的任务。连续核验失败后进入人工处置或按节点幂等能力重试。

## 13. 数据模型演进原则

现有 `chat_task`、`workflow_run` 和 `agent_run` 不做破坏性改写。新增迁移按以下方式渐进演进：

1. 新增 Runner 档案、统一运行、运行事件、审批和产物实体。
2. 新运行首先写统一运行实体，再由执行器写现有兼容表。
3. 前端与新 API 只读取统一状态；旧接口保持一个观察版本。
4. 完成数据与调用对账后再决定是否合并旧表，绝不在本阶段删除历史运行和审计数据。

建议的新实体职责：

| 实体 | 职责 |
| --- | --- |
| `agent_executor_profile` | 内置或远程执行器地址、协议、凭据引用、清单与健康状态 |
| `agent_execution` | 统一运行身份、版本快照、状态、发起人、时限与结果摘要 |
| `agent_execution_event` | 只追加的脱敏运行事件 |
| `agent_execution_approval` | 审批请求、决定、操作者和版本 |
| `agent_execution_artifact` | 运行产物元数据与访问控制 |
| `workflow_definition` / `workflow_revision` | 草稿与不可变发布图定义 |

具体列、索引和外键在实现计划中以查询模式和保留策略为依据确定。数据库变更只新增后续迁移，不修改 `001` 至现有迁移。

## 14. 部署策略

当前继续使用 Docker Compose：

```text
api
chat-runner / workflow-runner
worker
frontend
complex-agent-bid
complex-agent-erp
complex-agent-drawing
```

复杂智能体按需独立构建、升级和限制资源。平台与 Runner 镜像版本分别管理，发布记录保存二者版本组合。

本阶段不引入 Kubernetes、通用消息中间件或第二套低代码平台。只有出现多节点调度、服务数量显著增加、可测量的弹性/可用性需求，且单机资源不再满足时，才评估 Kubernetes。多 Runner 横向扩展前必须先完成任务租约、owner、心跳和过期接管，不能依靠编排平台自动解决重复执行。

## 15. 测试策略

### 15.1 契约测试

- Runner 清单、输入输出 Schema、幂等创建、取消和事件续传。
- 平台 SDK 的模型、知识、MCP、审批、产物和工作流调用。
- 新旧 Runner 版本兼容和拒绝不兼容发布。

### 15.2 权限与安全测试

- 部门越权、撤权后续调用、过期/错误 audience 令牌。
- Runner 伪造用户、扩大知识库/工具范围和重复回调。
- 任意地址、重定向、超大事件、恶意 Schema、敏感日志和产物越权。

### 15.3 工作流测试

- 分支选择、汇聚、变量映射、子流程和 Agent 节点。
- 节点重试、幂等、取消、超时、Runner 崩溃和恢复。
- 人工审批前后权限变化、重复审批和并发审批。

### 15.4 端到端验收

使用虚构数据建立一个低风险试点：

```text
表单输入 → 知识检索 → 调用示例复杂智能体 → 人工确认
        → 只读 MCP 查询 → 生成产物 → 下载与审计
```

验收必须验证页面离开/刷新后恢复、取消、失败重试、版本固定、权限撤销、事件顺序和产物访问，不调用生产写工具。

## 16. 分阶段实施

### 阶段一：运行基础与复杂智能体接入

- 建立执行器档案、统一运行、事件、审批和产物模型。
- 实现 Runner 契约、委托令牌、平台能力网关和最小 SDK。
- 实现一个无业务副作用的示例复杂智能体。
- 在 Agent 管理中配置执行器，并在现有任务页面展示统一事件和产物。

### 阶段二：工作流执行语义

- 将现有顺序步骤迁移为版本化图定义。
- 增加条件、转换、Agent 调用和子流程节点。
- 完成类型检查、失败策略、幂等、恢复和统一事件。
- 保持现有工作流 API 兼容并完成对账。

### 阶段三：可视化编排与发布

- 建设 Vue 工作流画布、节点配置、调试和运行时间线。
- 建设草稿、校验、评测、发布、回滚和权限摘要。
- 将 Agent 目录升级为带版本、负责人、指标和风险标签的市场。

### 阶段四：扩展与企业治理

- OIDC/LDAP SSO、业务骨干受限创作和发布审批。
- Token/成本、容量、并发、预算、告警和灰度发布。
- 根据实际生态增加 A2A 适配、事件触发和多实例租约执行。

## 17. 不在本次范围

- 允许普通员工执行任意代码、SQL、shell 或任意 HTTP。
- 将 Dify、n8n 或其他平台作为第二套身份、知识库和模型控制面。
- 直接开放 ERP/PLM/MOM 写操作。
- 为展示效果先实现画布、后补执行语义。
- 立即拆成微服务、引入 Kubernetes 或消息中间件。
- 自动把已有复杂项目包装为 Runner；每个项目仍需实现并通过接入契约测试。

## 18. 完成标准

- 至少一个独立复杂智能体可通过统一契约注册、发布、运行、取消、上报事件和生成产物。
- Runner 只能使用当前用户和智能体授权交集内的模型、知识库和 MCP 工具。
- 工作流可以通过 `agent_call` 固定版本调用复杂智能体，并可在失败、取消、超时和人工确认后可靠恢复。
- 前端对内置问答、工作流和远程智能体使用统一运行状态、时间线和产物展示。
- 配置、Runner、工作流和授权均版本化；历史运行可重现其版本组合。
- 权限、安全、幂等、恢复、契约和端到端测试通过，现有知识库、对话与 MCP 功能无回归。
