# 结构化文档解析（builtin-structured 0.8.0）

## 本次处理规则

### PDF

- pdfplumber 提取文字坐标、字号、带线框表格，按版面先后输出文字和表格。
- 仅在页面顶部/底部 8% 区域处理页眉页脚：明确页码可删除；其他文字必须在至少两页、且不少于半数页面重复才删除。正文区域的重复条款不会因此删除，不把业务数字统一替换后匹配。
- 跨页续段要求相邻页、上一页内容接近页底（78% 以下）、下一页接近页首（22% 以内）、左边界相近，而且上一段未以完整结束标点结尾、下一段不是新章/条目。证据不足保留原边界。
- 跨页续表目前识别**相邻页边界、相同非空表头、相近左右边界**的线框表格，复用表格编号和列名，不把重复表头当数据行。不会仅凭列数相同就合并。
- 每个切片保留真实的 `page_start`、`page_end`。跨页片段的引用显示页码范围；这两个字段描述片段涉及的页范围，不声称所有句子都来自整个范围。
- 每页单独判断是否需要 OCR，解决一份 PDF 中既有文字页又有扫描页的情况。OCR 按页渲染并释放图像，不一次渲染整本扫描文件。

### Word（DOCX）

- 按文档正文 XML 顺序遍历段落、标题、表格，不再先提取全部正文再追加表格。
- 保留标题样式及直接设置的 outline level；标题路径带入所属段落/表格切片，新标题下的内容不与上一节混为一组。
- 表格按行输出，携带表头和表格编号。Word 不提供可靠渲染页码，不伪造页号。

### Excel（XLSX / XLSM）

- 按工作表、空行分隔的表格区域分别处理。每个表格切片重复工作表名、表名（若识别到）和表头，数据带物理行号及“列名：值”。
- 常规文本表头、开头单行表名，以及有合并单元格辅助证据的多级表头（最多三行）可识别。合并单元格只用于解释表头，不向下填充正文，避免制造数据。
- 缺少可信表头时用“列1、列2”等标签，不丢弃首行数值；`0` 和 `False` 不当空值删除。
- 公式读取 Excel 已保存的缓存值，不执行公式/宏；无缓存公式结果可能为空，需先用 Excel/LibreOffice 计算并保存。

## 切片与存储

- 默认长度仍为 1200 字符、重叠 150 字符；标题/表头计入长度。
- 对超长文本增加有界切分（优先换行、标点，再兜底字符切分），不再允许一行无限超长。实际重叠不超过可用正文预算的四分之一。
- 过宽表头/过长标题导致上下文放不进切片时，任务明确失败并提示拆表或缩短标题，不静默截掉列名。
- 已有 `content_unit.metadata_json` 记录解析器版本、来源格式、标题、工作表、表格编号、行号和各来源范围。使用原有页码字段，无需数据库迁移；Milvus 集合结构和 Embedding 模型不变。
- 新上传文件使用新规则；已有文档维持原切片，只有用户主动“重建”才会重新解析、切片、向量化和写入全文索引。部署不自动批量重建。
- 本次不是父子切片，也没有引入 LangChain/Unstructured。

## 已知边界

这是可测试的保守规则，不是通用文档版面模型。多栏 PDF、旋转文字、无框表格、没有重复表头的续表、跨页拆开的单元格、扫描表格的复杂单元格关系，仍需人工抽查，不能保证结构正确。扫描页目前 OCR 为带坐标文本，不宣称已恢复完整表结构。

表头自动识别无法在所有纯文本表格上确定哪行是表头；不规则、多表头台账应先规范格式。嵌套 Word 表格、文本框、修订痕迹、复杂域、嵌入对象不是本次完整支持范围。不能将图纸解析能力等同于 PDF 文本/线框表格提取。

## 验证与部署

测试不接触现有数据库，不调用外部模型。真实格式的临时 PDF/DOCX/XLSX 由测试在临时目录中构造。

```bash
python -m pip install -r services/worker/requirements.txt pytest==8.3.5
python -m pytest tests/test_parsing.py -q
cd services/frontend
npm ci
npm run build
```

将本次代码同步至服务器后，从项目根目录运行（保留原 `.env` 和数据目录）：

```bash
docker compose --env-file .env -f deploy/docker-compose.yml -f deploy/docker-compose.models.yml up -d --build --no-deps worker api frontend
```

API 和前端需要一并更新才能在回答引用中显示结束页号；只更新 Worker 仍可入库，但旧页面仅显示起始页。
