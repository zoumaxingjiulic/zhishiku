# 项目审查与本轮整理（2026-09-30）

## 审查范围与结论

检查了仓库内的部署配置、数据库迁移台账、FastAPI 模块边界、前端页面与样式入口、自动化测试和 CI。当前系统是单机模块化单体：API、文档 Worker、chat-runner 分进程运行；MySQL 承担任务状态，MinIO、Milvus、OpenSearch 各有独立用途。没有证据表明这些核心组件可以安全合并或删除。

本轮只移除可证明没有业务调用的 Redis 运行依赖，整合重复的全局样式入口，并修复前端对非 JSON 成功响应的误判。没有删除数据库表、历史迁移、对象数据、向量数据或现有服务器目录。

## 保留而不做破坏性清理

- `database/mysql/001` 至 `014` 是已发布迁移历史；旧表是否能删除，需要先有生产读写观测、备份和迁移方案，不能从文件名判断。
- `.env`、`data/`、模型权重、用户上传文件和本机既有未跟踪目录均不纳入代码清理。现有服务器上的 Redis 数据目录至少保留一个观察版本，以便回滚核对。
- 历史设计/实施记录用于解释版本演进，不按当前运行配置批量改写。

## 尚需上线验收的边界

自动化测试和本地预览不能替代真实容器与业务数据验收。应用到服务器前，先备份并记录当前版本，再在维护窗口核对 Compose 差异；启动后检查 `/healthz`、`/readyz`、登录、不同部门权限、文件上传与检索、总助手/专业智能体会话、MCP 只读调用和审计记录。确认 Redis 已无外部消费者后再停止旧容器，不执行 `down -v`，不删除 `${DATA_ROOT}/redis`。

正式生产推广仍需完成 HTTPS、安全 Cookie、定期备份与恢复演练、容量/并发压测、监控告警，并固定 Infinity 镜像版本。当前 Worker 与 chat-runner 的启动恢复逻辑只支持各单实例，不能直接水平扩容；详见 [后端架构说明](architecture.md)。
